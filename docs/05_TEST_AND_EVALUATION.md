# Tests and evaluation gates

## Unit cases with explicit expected outcomes
1. Confirmed + fresh active exploitation -> P1/P-01 regardless of low severity.
2. Exposed + critical asset + high severity, no active evidence -> P1/P-02.
3. Critical severity + standard internal asset -> P2/P-03; do not simply demote because internal.
4. High severity + standard not_exposed -> P3/P-05.
5. Unknown severity -> P2/P-06, severity_unknown.
6. Missing asset -> retained, unknown context flags; never disappear.
7. not_affected + active evidence -> EX-01/null, preserved evidence; do not claim fixed.
8. Missing owner does not lower priority; row appears in review.csv.
9. 30-day context fresh; 30 days + 1 second stale. Same boundary tests for 7-day threat evidence.
10. Stale active evidence remains recorded and flagged; fresh not_observed does not erase it.
11. Fresh active plus fresh not_observed -> active and contradiction flag.
12. Unconfirmed low finding + active evidence -> P2/P-03 with applicability flag.

## Parsing and integration
Test invalid enums, duplicate headers, missing headers, unknown columns, malformed CSV, blank IDs, empty optional fields, future/invalid timestamps, size limits, Unicode, duplicate/conflicting records, formula injection, Markdown injection, and output traversal handling. Empty valid dataset produces zero-count briefing, not fabricated top findings.

Check all input row counts reconcile after duplicate normalization. Fatal validation produces no published recommendation set. Test existing output directory behavior and failed artifact writes. Test exits 0/1/2/3. Fixed inputs/as-of/policy yield identical artifact bytes; ordering of threat rows must not change decisions. Reordering source rows may change source references/input hashes but not the mapped decisions.

## Golden synthetic dataset
Create 12-20 manually specified scenarios spanning the unit cases, using reserved domains and SYN vulnerability IDs. Write expected rule IDs and flags before running implementation. Expected answers must not be generated by calling the evaluator itself. Have the user review scenario rationales. Track policy fixture versions.

## Benchmark protocol
Compare severity-only ordering (critical, high, medium, low, unknown; same tie-breakers) with policy ordering. Show three changed positions with evidence. Excluded findings are excluded from both baseline comparisons and counted separately. A ranking change is not automatically an improvement.

For usability evaluation, ask available reviewers to perform the same defined triage task using baseline and tool. Counterbalance order if possible. Record sample size, data, timing method, disagreements and limitations. Never invent reviewers, time savings, accuracy or risk-reduction metrics.

For performance, generate a seeded synthetic dataset and measure actual runtime/peak memory on a disclosed environment. Stay within configured limits. Do not call the result enterprise scale or extrapolate without testing.

## Release acceptance
- Unit/integration tests and lint pass in CI on supported Python.
- Coverage emphasizes specified branches; coverage percentage is not evidence of policy validity.
- Three decisions independently trace to evidence and rules.
- Fixed-time replay passes.
- README demo commands verified from a clean environment.
- Threat model, limitations and dependency inventory current.
- Service release additionally requires docs/06 security gates.
